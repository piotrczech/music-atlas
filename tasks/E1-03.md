# Audio, annotation and licence audit

Audit FMA-full and use the findings to finalise the versioned datasets introduced in #5 / PR #13.
The current pre-audit manifests provide a working starting point, but inventory presence and
matching checksums do not establish that the audio is usable.

The goal is a documented path from the original catalogue to trustworthy train/validation/test
datasets, with explicit exclusions and a clear explanation of the remaining limitations.

### 1. Audit audio, annotations and licences

Read audio directly from the existing tar shards using the shared loader. Check decoding
failures, empty recordings, decoded duration, discrepancies with published metadata and
potentially problematic audio such as near-silence or unusually short recordings.

Distinguish technical failures from unusual but valid music. Do not automatically discard long
recordings, rare genres, noisy historical recordings or tracks with multiple labels. Define and
justify any exclusion thresholds, reporting their effect on genre and artist coverage.

Detect exact duplicates using the inventory hashes and investigate likely re-encodings using a
documented fingerprint or targeted comparison. Keep confirmed duplicates separate from
unresolved candidates. Record results by `track_id`, including validity, decoded duration,
exclusion reason and confirmed duplicate-group identifier, in the audit format that
`atlas fma-split --audit` expects (`docs/EXPERIMENTS.md`). Retain the source audio.

Inspect missing or inconsistent genre annotations and artist/album identifiers. Missing genre
tags must not be treated as verified negative labels. Document licence coverage and the
selection rule for distributable listening examples.

### 2. Review existing FMA preparation and evaluation practices

FMA is a widely used dataset with published splits and known issues. Review the original
dataset paper, official errata and relevant research or reproducible implementations before
settling on our final preparation rules.

Look for useful approaches to artist-disjoint splitting, multilabel stratification, rare-class
support, duplicate handling and artist concentration. Summarise the relevant methods and
explain which decisions we adopt or reject. Distinguish results directly comparable with an
established FMA benchmark from results using our own protocol.

Starting references:

- [FMA dataset paper](https://arxiv.org/abs/1612.01840)
- [Official repository and analysis notebooks](https://github.com/mdeff/fma)
- [Known issues and errata](https://github.com/mdeff/fma/wiki)

### 3. Resolve the split concerns identified in PR #13

The current notebook reports zero artist and exact-duplicate overlap in our generated splits.
However, disjoint artists do not guarantee diverse evaluation within each genre.

For example, the saved rare-support results show one artist supplying 87.7% of validation Blues
and 51% of validation Easy Listening. Even the proportional version has a test Spoken class with
46% of tracks from one artist. Increasing track counts can therefore increase apparent support
without providing enough independent musical examples.

In coordination with #5, assess and, where necessary, improve the allocation using genre
prevalence, independent artist/component counts and concentration within each genre and
partition. Preserve artist and confirmed-duplicate separation as hard constraints. Explain
unavoidable trade-offs rather than forcing exact proportions.

Use the audited catalogue to regenerate and validate the datasets:

- Keep one explicitly designated primary benchmark shared by every representation.
- Treat rare-support and balanced evaluation views as supplementary experiments with
  documented purposes.
- Keep train, validation and test from the same dataset version together. The rare-support
  strategy changes training membership too, so differences between versions cannot be
  attributed solely to test balancing.
- Select and freeze the split using documented data-quality criteria before comparing model
  performance.
- Record model-specific exclusions without moving tracks between partitions.

Publish versioned manifests, fixed label mappings, input/output hashes, per-split support
statistics and automated overlap checks. Report how many tracks were excluded for each reason
and how those exclusions affected individual genres.

### 4. Final deliverable: one data notebook from beginning to end

Merge the metadata exploration from #4 (`notebooks/fma_metadata.ipynb`) and the split
diagnostics from #5 (`notebooks/01-data-exploration.ipynb`) into a single
`notebooks/01-data-exploration.ipynb`, then remove `fma_metadata.ipynb`. It is the notebook a
developer opens first to learn what data we work with, what is wrong with it, how we clean it
and how we split it. Keep only figures and tables that support that story or a decision taken
here; drop exploratory views, duplicated tables and configuration knobs that do not. Present
the process in order:

1. Describe the original catalogue, label hierarchy, imbalance and artist concentration.
2. Present the audit results and illustrative problematic cases.
3. Show which tracks were retained, excluded or left unresolved, why, and the resulting
   coverage changes.
4. Explain the grouping and splitting methods, alternatives considered and selected trade-offs.
5. Compare the published FMA split with our final versions, showing genre support, artist
   concentration and leakage checks.
6. Identify the primary benchmark and supplementary views, their intended metrics and remaining
   limitations.

The notebook should make every final dataset traceable to its inputs and preparation rules.
Save aggregate results so the reasoning is reviewable without access to WCSS, and document how
to reproduce them.

Run the audit and dataset generation as CPU SLURM jobs, writing consolidated tables to the
configured project storage. Use OOD notebooks for inspection.
