# Window length and preprocessing study

Compare a small, predefined set of window lengths, such as 5, 10 and 20 seconds, on the same
fixed development tracks and offsets. Use the shared loader and log-mel transform to examine how
duration changes captured musical events, tensor size, extraction time and memory. Keep sample
rate and spectral parameters fixed during this comparison; investigate an additional
preprocessing choice only as a separate controlled comparison.

Produce matched visual examples and a short results table with an interpretation of the
trade-off. This task informs the default research window and the later CNN experiments before a
full training campaign is committed. It should not depend on a trained CNN being available or
introduce a different dataset split.

### Starting from stage 1

- Use the 128-track quick sample as the fixed development tracks, so every member compares the
  same audio locally.
- `load_windows` takes `window_seconds` and centres one window in the quick profile, so 5, 10
  and 20 s windows share the same centre without other changes.
- Use the log-mel transform from E2-04 once it exists; until then fix its parameters
  explicitly in this study.

### Tracking (E2-01)

- Record each run with `music_atlas.tracking.track()` and expose it as `--track`; `atlas
  quick-sample --track` is the reference and the `atlas-tracking` skill the convention. Call
  `run.log_dataset` once per partition read: counts that describe the data go there, metrics
  hold only what the step measured. On WCSS, `sbatch ... --track` logs to PD and
  `scripts/mlflow-ui.sh --wcss` shows the runs locally.
- One run for the study: the window length is what varies, so log its results nested by
  length (`{"w5": {...}, "w10": {...}}`), the results table and matched examples under
  `evaluation/`, and say in `description` which factor changes. The profile's own
  `window_seconds` param stays the reference.
