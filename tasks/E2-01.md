# Experiment runner and MLflow integration

Provide a shared way to run an experiment from a quick/full configuration and record it in
MLflow. Reuse the existing CLI and configuration loading rather than introducing a separate
workflow framework. Each run should capture the Git revision, seed, resolved parameters,
manifest hash, processed counts, elapsed time and metrics, with artifacts written to a
predictable run directory. Support file-based tracking on WCSS when a tracking server is
unavailable.

Integrate one small end-to-end run to establish the naming and logging convention used by the
three representation branches. Failed or resumed processing must remain distinguishable from
completed results. Document how to compare runs and retrieve the exported model or vectors
without coupling the serving application to a live MLflow process.

### Agreed approach: file tracking on PD, viewed through Open OnDemand

Checked on WCSS in November 2026:

| Option | Status |
|---|---|
| `ssh -L` through `ui.wcss.pl` | Works; the account key allows port forwarding |
| Outbound internet from compute nodes | Works (`wcss-slurm` skill, NET-01) |
| OOD proxy to any port on a compute node | Works: OOD sessions are served at `https://ood.e-science.pl/node/<host>/<port>/`, behind e-science SSO |
| Server on the login node | Not allowed: 1 GiB RAM per user, not a service host |
| Server kept running as a job | Too costly: billing is cores × wall time, so one core for 21 days is about 500 of our 4,000 CPU-hours |
| `sshfs`, transfer node, MLflow app in OOD | Not available |

Jobs log while they run; nobody keeps a server up:

1. **Logging.** The runner reads `MLFLOW_TRACKING_URI` from the environment. On WCSS,
   `~/.atlas-env.sh` sets it to `file:$ATLAS_OUTPUTS_DIR/mlruns` (MLflow rejects runs below a
   folder named `artifacts`); locally it points to `outputs/` or a local server. The file store writes each run to its own files, so parallel
   jobs do not collide. Do not use SQLite on PD: concurrent writers and Lustre locking break it.
   Large outputs (vectors, models) stay in `artifacts/<representation>/<run_id>/`; MLflow
   records their paths, metrics and parameters.
2. **Viewing on WCSS.** `scripts/mlflow-ui.sh --ood` starts the UI inside an OOD Jupyter
   session (`lem-cpu-interactive`, 1 core, billed only while open) and prints its
   `https://ood.e-science.pl/node/<host>/<port>/` link. `--static-prefix` matches the proxy
   path; the proxy sends the node as `Host` and OOD as `Origin`, which the script allows.
   Verified end to end in November 2026; Lem only, since the UI needs AlmaLinux 9.
3. **Viewing locally.** `scripts/mlflow-ui.sh --wcss` mirrors `mlruns/` from PD with `rsync`
   and runs `mlflow ui`; this uses no grant hours. A tunnel (`ssh -L 5000:<host>:5000 ui.wcss.pl` to a `srun` job) also works
   but adds nothing over OOD.

Later option: compute nodes reach the internet, so jobs could log over HTTPS to a hosted MLflow
(such as DagsHub or a small VPS) for an always-on team UI. That needs only a different
`MLFLOW_TRACKING_URI` and a token in `~/.atlas-env.sh`; metrics would then leave WCSS.

### Starting from stage 1

- Extend `music_atlas.cli` and `music_atlas.settings.profile()` rather than adding a framework;
  the profiles in `configs/quick.toml` and `configs/full.toml` already hold the seed, window
  settings and `[dataset] split` (the dataset version).
- Take the dataset identity from `ready/<version>/summary.json` (`version`,
  `manifest_sha256`); `atlas quick-sample` already records the same fields in `sample.json`.
- `mlflow` is in the locked `tracking` extra. The first end-to-end run can be a small step on
  the quick sample, for example loading every window and logging counts and timing.
