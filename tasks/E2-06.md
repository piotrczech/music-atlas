# Pretrained encoder selection and embedding extraction

Select one pretrained music/audio encoder after checking its model card, licence, checkpoint
availability, input requirements and likely training-data overlap with FMA. CLAP is a candidate,
but the choice should follow a quick-sample pilot measuring extraction speed, memory and the
behaviour of representative music examples. Record the selected checkpoint revision and apply
its required preprocessing without changing the shared window positions.

Implement resumable extraction for every track of the three partitions and aggregate windows
into one track vector using an explicit rule. Save aligned track IDs, vectors and metadata in
the shared representation format. The resulting embeddings must support both a frozen-encoder
classifier and retrieval without rerunning corpus extraction for each experiment or query.

### Starting from stage 1

- Window positions do not depend on the target sample rate: `load_windows(...,
  sample_rate=48000)` returns the same time spans resampled for an encoder that needs 48 kHz.
- GPUs are on Lem only (`--gres=gpu:hopper:1`, at most 16 cores per GPU, `docs/DEVELOPMENT.md`).
  Sync the `training` extra into node-local `TMPDIR` rather than onto Lustre. Compute nodes
  reach the internet, and `HF_HOME` in `~/.atlas-env.sh` keeps downloaded checkpoints on PD.
- Run the pilot on the quick sample first and size the GPU job from it; GPU hours (300) are
  scarcer than CPU hours.

### Already provided: `music_atlas.representation`

The shared part of extraction is done and tested; this task supplies the encoder, a plain
function `encode(samples) -> vectors` from `(n_windows, n_samples)` float32 mono at the
encoder's sample rate to `(n_windows, d)`. No base class is needed.

- `extract(data_dir, run.directory, encode, sample_rate, metadata, profile_name,
  windows_per_track, limit, record=run)` reads the profile's tracks shard by shard through
  `music_atlas.shards` and encodes batches of 64 windows in this process, so a GPU model is
  loaded once. A killed job resumes from its finished shards with `track(..., resume=run_id)`.
- It writes `vectors.npy` (the mean of each track's windows) with `track_ids.npy`, and also
  `window_vectors.npy` with `windows.parquet`, so another aggregation needs no second
  extraction. `metadata.json` names the encoder and revision; `failed.csv` lists tracks the
  loader rejected.
- `windows_per_track=5` encodes 50 s instead of 30 s per track; windows 0, 2 and 4 are the
  default three, so one run serves both variants. Decide from the quick pilot whether five pay
  off on the GPU budget.
- Zero padding of tracks under 10 s halves their mean level; CLAP's own extractor repeats
  short audio instead (`padding="repeatpad"`), so let the encoder's preprocessing handle it.

Suggested order of the remaining work:

1. Finish the comparison of candidates (the CLAP checks on WCSS already record revisions and
   Apache-2.0 licences): input sample rate and length, training data and possible FMA overlap.
   Write a short table.
2. For each candidate, write `encode` (load the model once, run it under `torch.no_grad()` on
   the GPU) and run `extract` on the quick sample. Log `torch.cuda.max_memory_allocated()` as
   `gpu_memory_mib`, check a few nearest neighbours by ear, and put the comparison under
   `evaluation/`.
3. Add `atlas embeddings --encoder ... --profile ... --windows ... --track [--resume RUN_ID]`
   to the CLI (`atlas log-mel` is the reference) and an sbatch script for Lem. Size the full
   job from the quick `tracks_per_second`.

```python
with track("embeddings", profile_name, storage, representation="clap",
           overrides={"windows_per_track": 5},
           description="LAION-CLAP music checkpoint, mean of window embeddings.") as run:
    extract(storage["data"], run.directory, encode, 48000,
            {"encoder": "laion/larger_clap_music", "revision": "<commit>"},
            profile_name, windows_per_track=5, record=run)
```

### Tracking (E2-01)

- Record each run with `music_atlas.tracking.track()` and expose it as `--track`; `atlas
  quick-sample --track` is the reference and the `atlas-tracking` skill the convention. Call
  `run.log_dataset` once per partition read: counts that describe the data go there, metrics
  hold only what the step measured. On WCSS, `sbatch ... --track` logs to PD and
  `scripts/mlflow-ui.sh --wcss` shows the runs locally.
- Pass a `representation` named after the encoder: embeddings go to
  `artifacts/<representation>/<run_id>/` with `metadata.json` naming the checkpoint and its
  revision. Log extraction speed and GPU memory as metrics; continue a failed job with
  `track(..., resume=run_id)`. The pilot comparison of candidates goes under `evaluation/`.
