# Catalogue-wide acoustic feature extraction

Implement batch extraction of MFCC, chroma, rhythmic and spectral features using the shared
loader and manifest. Define a compact feature schema, including the temporal statistics and
window aggregation used to produce one vector per track. Keep identifiers and preprocessing
metadata with the saved features, and make non-finite or unavailable measurements visible in the
extraction report rather than replacing them silently.

Validate the pipeline on the quick sample, measure throughput, then process every track of the
three partitions on WCSS. Write resumable shards or another bounded output format so that a
failed job does not discard completed tracks. These vectors feed the classical classifiers,
feature interpretation and acoustic nearest-neighbour search, so their order and column names
must remain stable.

### Starting from stage 1

- Read `train.parquet`, `validation.parquet` and `test.parquet` of the profile's dataset
  version and audio through `load_windows`, shard by shard (data notebook, section 4). The
  partitions hold exactly the audited valid tracks (106,279), so nothing needs filtering first.
- About 1,900 valid tracks carry an audit warning: under 10 s (one zero-padded window), very
  quiet, or shorter than FMA lists. They load fine, but quiet or padded windows can make chroma
  or tempo undefined; report such values instead of filling them silently.
- FMA ships `fma_metadata/features.csv` (518 librosa statistics per track). We do not use it,
  but it is a quick sanity check for the ranges of our own features.
- Measured throughput: about 4 s to open a shard and 0.06 s per quick window; feature
  computation comes on top and decides the full-job size.

### Tracking (E2-01)

- Record each run with `music_atlas.tracking.track()` and expose it as `--track`; `atlas
  quick-sample --track` is the reference and the `atlas-tracking` skill the convention. Call
  `run.log_dataset` once per partition read: counts that describe the data go there, metrics
  hold only what the step measured. On WCSS, `sbatch ... --track` logs to PD and
  `scripts/mlflow-ui.sh --wcss` shows the runs locally.
- Pass `representation="acoustic"`: vectors, `track_ids.npy` and `metadata.json` go to
  `artifacts/acoustic/<run_id>/`, and `metadata.json` (feature schema, aggregation) is attached
  to the run. A failed full job continues with `track(..., resume=run_id)` in the same
  directory as a new attempt. Log failed tracks and `tracks_per_second` as metrics and the
  non-finite value report under `dataset/`.
